# Backend and Godot contract review — 4 October 2026

Verdict: the modular NestJS structure is a useful foundation, but the current source is not ready for a public production launch. The highest priorities are functional correctness, atomic state transitions, authentication abuse protection, and recoverable match completion. A framework rewrite is unnecessary.

Scope: all 50 backend TypeScript source files, Prisma schema and deployment configuration, active Godot authentication/backend/game networking, controllers, mode lifecycle, packet codecs, and related client rendering integration. Generated dependencies were inspected where necessary to verify exception and email behavior. Legacy client_controller_old.gd and generated Android build artifacts are not treated as the active contract. No production environment, database, email service, or deployed container was exercised. Findings concern this checkout; external infrastructure may provide controls not represented here.

**Release-blocking findings**

1. **[P1] Dedicated server instantiates client mode scenes.** `godot/server/server_controller.gd:3–8` maps every mode to a `_client.tscn`. At lines 54–56 it assigns `players`, `bots`, and connects `gameover`, which those scenes do not expose. A headless Godot 4.7.2 probe confirmed all three are absent in both scene types. Startup cannot reach the intended ready handshake. Point this registry at `womp_server.tscn` and `draft_server.tscn`; validate configuration and test an actual dedicated-server startup for every mode.

2. **[P1] Shipping clients are hardcoded to localhost and cleartext transports.** `godot/client/client_auth_net.gd:9` and `godot/client/client_backend_net.gd:12–13` use `127.0.0.1`, HTTP and WS. On a phone, that address targets the phone. Introduce one environment-specific endpoint configuration and HTTPS/WSS for remote production connections. Refresh tokens are also saved directly in a ConfigFile; use platform-protected credential storage for releases. The game ENet connection has no explicit transport-security setup; assess secure transport for the reusable bearer game token rather than assuming hashing it on the server protects transmission.

3. **[P1] Authentication endpoints have no application abuse controls.** `backend/src/auth/auth.controller.ts`, `auth.service.ts` and `main.ts` contain no throttling, OTP attempt counters or resend cooldowns. Six-digit codes can be guessed repeatedly; guest creation and email requests can consume unbounded database/email resources. Add per-IP and per-account/challenge limits, an atomic attempt budget, expiry and resend rules, and generic responses. Guest accounts can also repeatedly request game containers, so admission limits must cover matchmaking.

4. **[P1] Token rotation and OTP consumption are not atomic.** `backend/src/auth/auth.service.ts:61–100` reads a refresh hash then updates by session ID alone. Two concurrent requests can both succeed; only the final hash survives. An isolated probe returned two successful refreshes but only one valid returned refresh token. Godot's `_get_valid_access_token()` has no shared in-flight refresh, making this possible with overlapping authenticated requests. Use a conditional compare-and-swap including old hash, revocation and expiry; serialize refresh in the client and define response-loss/retry behavior. `verifyLogin` and `verifyLink` similarly read `usedAt` and update later, allowing concurrent reuse. Consume a challenge conditionally in the same transaction as its intended operation.

5. **[P1] Invalid JWTs become HTTP 500 instead of 401.** `backend/src/auth/auth.service.ts:280` lets `JwtService.verifyAsync` errors escape. `AuthGuard` does not translate them. A probe confirmed `JsonWebTokenError` is not a Nest HTTP exception; the installed default exception filter handles it as an internal error. Normalize invalid/expired tokens to 401. Godot also hardcodes a 900-second TTL while Nest reads `JWT_EXPIRATION_MS`, and `_authenticated_request()` never refreshes/retries on 401. Return token expiry, share refresh work, and retry a request once after authentication rejection with suitable mutation semantics.

6. **[P1] Lobby mutations race across database awaits.** `backend/src/lobbies/lobbies.service.ts:113–156, 249–263, 375–423`. Two concurrent connects create two lobbies for one indexed player; this was reproduced with a deferred database mock. Concurrent invite acceptance can both pass the capacity check before either pushes a player, exceeding capacity. A lobby can also enter matchmaking while a join is awaiting its player fetch, leaving roster and ticket inconsistent. Fetch prerequisites before mutation, then serialize/recheck operations for affected players and lobbies. Check that a connection is still current before applying its async initialization. A failed join must preserve the player's prior membership.

7. **[P1] Match state and completion guarantees disappear on restart.** `backend/src/game-servers/game-servers.service.ts:19–21, 67–220`, and the Prisma schema. Active games, callback token hashes and completion deduplication exist only in memory. Restarting Nest loses callback authorization for still-running servers, reconnect information, and undelivered results. A database commit followed by process failure can leave trophies changed without a durable completion record. Store matches, participants, results and completion identity in PostgreSQL; write rewards and completion atomically under a unique game ID. Add durable delivery/replay and startup reconciliation with the container runner. Multiple Nest replicas are currently unsafe because lobbies, queues and socket routing are also process-local.

8. **[P1] Match completion validates shape, but not match invariants.** `backend/src/game-servers/game-servers.service.ts:80–101` dereferences an unknown participant with a non-null assertion. The DTO allows arbitrary positive placements and any nonempty loadout strings. Unknown IDs cause a server error; omitted players fail ranked settlement, while incomplete unranked results can be accepted. It also permits contradictory teammate placements and multiple winning teams. Require exactly the expected participant set, mode-valid team rankings, valid item IDs and the appropriate match lifecycle state. Preserve legitimately drafted loadouts, rather than always replacing them with initial loadouts. This endpoint is protected by a per-game secret: this is a server-contract integrity issue, not an assertion that ordinary clients can submit results.

9. **[P1] Public API has unrestricted Docker-daemon access and no game admission budget.** `docker-compose.yml` mounts `/var/run/docker.sock` into the backend. `startGame()` launches containers without CPU/memory/PID limits or an overall concurrency cap. A backend compromise therefore has a much larger host-level impact, and normal account creation can be abused to allocate game processes. Isolate container orchestration behind a narrowly scoped worker/API, add admission quotas and resource limits, and define maximum match lifetimes and cleanup. Docker's official security documentation explains the daemon's privileged attack surface: https://docs.docker.com/engine/security/ .

**Reliability and contract findings**

10. **[P2] WebSocket identity can be rebound without removing the old identity.** `backend/src/realtime/realtime.service.ts:17–26` sets player B for an already-authenticated socket without removing the player A forward mapping. A probe confirmed the socket continues receiving A-targeted events after rebinding. Disconnect then cleans only B. This requires valid tokens for the identities involved, but can retain private events and corrupt online presence. Reject identity switching or explicitly unregister both directions before replacement. Repeated authentication also reruns connection initialization. The analogous bidirectional-map pattern exists in `godot/server/server_game_net.gd:113–136`; make game authentication idempotent and bind a peer to one identity.

11. **[P2] Logout does not invalidate access or an authenticated socket.** `auth.service.ts:264–289` marks the session revoked, but JWT verification never checks that session, and realtime retains only the player identity. An existing socket can remain active indefinitely, beyond JWT expiry. Decide and document access-token revocation semantics; bind sockets to session IDs and expiry, terminate them on revocation, and provide a renewal protocol. Add WebSocket authentication deadlines, ping/pong liveness, connection/message limits and send-buffer limits. Half-open connections currently retain lobby presence until the transport notices them.

12. **[P2] Login and email linking use indistinguishable challenges.** `auth.service.ts:136–173, 176–261` and `EmailVerificationCode` lack a purpose. Login looks up the latest challenge by email alone, including a linking challenge. Linking also consumes the code separately from updating the player; a uniqueness failure can burn the code without linking. Use challenge IDs, explicit purposes and transactional ownership checks, and define whether already-linked accounts may change email. Invalidate obsolete challenges when ownership changes.

13. **[P2] Game-over delivery is not recoverable, and ordering can hide results.** `endGame()` emits lobby reopening via `gameClosed$` before `gameOver`. `godot/client/client_controller.gd` moves a MATCHMAKING client to LOBBY on the open-lobby event, then ignores `gameOver` outside GAME/MATCHMAKING. A player whose match ends before successful joining can miss the result. Disconnected players also have no result fetch/replay path. Store final results and include `gameId` in all lifecycle messages; process completion by match identity independently of the current UI state.

14. **[P2] Reconnect destroys an open party.** `lobbies.service.ts:260–263, 278–279` removes an open-lobby player on disconnect and creates a solo lobby on reconnect. A brief network change dismantles a party. Use a bounded presence grace period and resume the same membership when possible. Explicitly define matchmaking cancellation/abandonment: the current disconnected ticket remains queued and `cancelLobby` is private, so an offline player can still be assigned a ranked match and lose trophies.

15. **[P2] Ports are reused without checking active allocations.** `game-servers.service.ts:368–379` wraps a counter without checking current games or whether an old container has stopped. Once the port range cycles, Docker can fail binding a still-active port. Reserve free ports, reject/defer when capacity is full, and release only after confirmed container cleanup. Include reconciliation after restarts. Startup timeout is present, but there is no ready-server heartbeat or maximum lifetime for a hung match.

16. **[P2] Network decoders accept malformed payloads.** `godot/packets/input/input_batch.gd:25–33` trusts the count byte without checking the payload is exactly `1 + count * 8` bytes. `GameRequest.from_dict()` directly indexes unchecked keys; game RPCs impose no application message-rate limits. Validate lengths, counts, enum values, weapon values and bounded input tick windows before buffering. Snapshot counts use single bytes without constraining the serialized bullet/event arrays; an array beyond 255 cannot be faithfully represented and can misalign decoding. Add codec boundary tests and explicit payload budgets. The simulation remains server-authoritative; accepting input is not the same as accepting arbitrary positions.

17. **[P2] No versioned compatibility contract.** HTTP DTOs, WebSocket events, Godot dictionaries and binary item indexes are maintained independently. `gameReady` has no game ID/version; `receive_init` sends only mode/map; `Snapshot` maps items through the ordered arrays in `Data`. Reordering an item array across releases changes wire meaning, and unknown indexes silently become the first item. Add a protocol/content version handshake and stable numeric IDs or a negotiated manifest. Reject incompatible versions clearly. The init payload should include the full match roster: today the client knows only its lobby's names, so opponents and bots fall back to UUID display names.

18. **[P2] Email delivery failures are ignored.** `backend/src/email/email.service.ts:14–20` awaits Resend but discards its `{data,error}` result. The installed SDK returns error values for provider and transport failures. Requests can therefore report success when no email was delivered. Inspect the error, record redacted diagnostics/metrics, and use bounded queued retries. Preserve account-enumeration-resistant responses.

19. **[P2] Deployment has no migration history or startup validation.** `backend/Dockerfile:18` runs `prisma db push` on application startup; no migration directory exists. Commit and review migrations, baseline existing databases if needed, and use the version-appropriate deployment command in a controlled release step. For installed Prisma 7, see https://www.prisma.io/docs/cli/v7/migrate/deploy . The Dockerfile prunes development dependencies although Prisma CLI is declared as a dev dependency; make the migration tool explicitly available and pinned rather than relying on `npx` resolution at startup. Validate numeric config, durations, URLs, port ranges and secrets before accepting traffic. Add database-aware readiness, liveness and graceful shutdown/draining; `depends_on` alone does not check database readiness.

20. **[P2] No automated safety net.** There are no backend unit tests; `npm test -- --runInBand` exits 1 with “No tests found”. The e2e script references a missing `test/jest-e2e.json`. No CI configuration was found in the reviewed root/backend paths. Add state-transition, concurrency, database transaction and cross-language contract tests first. Passing lint and TypeScript does not detect the scene-registry failure or protocol mismatches.

Additional improvements: structured logs with request/game/player correlation and token redaction; metrics for match allocation, startup, callbacks, queue time and disconnects; bounded friends/invite APIs and expiration cleanup for stored sessions/codes/invites; documented database backup/restore procedures; graceful termination of subscriptions, timers and Prisma connections. The client friend-invite UI also indexes `response["data"]["invite_url"]` without checking success, so request failures can cause a script error. These are secondary to the release blockers above.

**Current contract assessment**

| Boundary | Current agreement | Missing guarantees |
|---|---|---|
| Guest/refresh HTTP | `displayName`, `refreshToken`; responses use `access_token`/`refresh_token` consistently | Authoritative expiry, atomic rotation, recovery and rate limits |
| Lobby/friend HTTP | Client paths and request names match controllers; 204 is handled by HttpUtils | Concurrent mutation safety, retry semantics, visible error handling |
| Backend WebSocket | Both sides use `{event,data}` and matching event names | Session binding, replay, versions, bounded liveness and one coherent reconnect snapshot |
| Nest → Godot configuration | Keys for game/mode/map/players/bots/tokens/callback URL match | Server mode registry, validated config, content compatibility |
| Godot → Nest callbacks | `/game-servers/:id/ready` and `/end`, bearer callback secret and result field names match | Semantic result validation, durable idempotency and recovery |
| Godot ENet | RPC names, node paths and transport modes match; server maps authenticated peers to players | Typed init/roster, version handshake, malformed-packet rejection and rate limits |
| Binary state/input | Same source codecs used on both ends | Stable wire IDs, length/count bounds and compatibility fixtures |

**Verification performed**

- `tsc --noEmit`: passed.
- ESLint over all 50 source TypeScript files, without fixes: zero errors/warnings.
- Jest: no tests found; exit 1.
- Isolated current-source probes with mocked infrastructure reproduced stale WebSocket mappings, two-success/one-valid refresh rotation, duplicate lobby creation, and a non-HTTP JWT exception. These are not database-backed integration tests.
- Godot 4.7.2 headless scene instantiation confirmed missing server properties/signals in both selected mode scenes. The run also emitted a macOS certificate-store warning; it did not make network requests.
- No real match, Docker build, database migration, dependency vulnerability scan, mobile release or load test was run. No application code was changed by this review.

**Recommended delivery order**

1. Fix dedicated-server scenes and endpoint configuration. Add one smoke test for each mode through ready/join/end.
2. Fix auth status/expiry/rotation/OTP controls, identity binding and lobby concurrency, with regression tests.
3. Persist match lifecycle and atomic completion/rewards; add callback retries, result replay and restart reconciliation.
4. Version and validate the HTTP/WS/ENet contract; test mismatched client versions and corrupt packets.
5. Introduce controlled migrations, isolated container admission, resource limits, health checks, logs and CI. Verify backup/restore and deployment rollback in staging.

Keep the modular monolith initially. A single explicitly supported coordinator is reasonable while building durable recovery. Introduce shared coordination and routing before adding backend replicas; adopting microservices or Kubernetes is not itself a prerequisite for professional quality.
